# Skyrim LE DLL compatibility experiment

The optional MOD screen checks a DLL or a MOD folder selected from Files. Installed MODs also have a diagnostic action in their details. The check runs the SKSE initialization exports in an independent, bounded x86 interpreter. The result applies to initialization and the two data-free startup notifications inside that test environment.

The PE32 loader validates the x86 layout, section permissions, exports, import ownership and HIGHLOW relocations. Its mapped sections and temporary stack are ordinary data. A small table of virtual addresses provides the Classic SKSE release index and plugin handle, registration for `PostLoad` and `PostPostLoad`, Windows uptime, CRT memory operations and a bounded virtual heap. The interpreter supports common repeated copies and stores on checked memory ranges. `SCASB` supports both repeat conditions, checking and charging one byte at a time through the first stopping comparison. Unsupported imports, formats, instructions and SKSE calls have distinct results. Instruction count, bulk work and file/image sizes have explicit limits.

The legacy PE32 load configuration reader checks the security-cookie address, the sorted SafeSEH table and the relocation words for both pointers. The DLL's runtime owns cookie initialization. Each interpreted invocation tracks the x86 thread's exception registration head at `fs:[0]`. A registration record must belong to that invocation's guest stack and name an executable guest address. Normal returns restore the head. Windows exception dispatch remains unsupported in the interpreter. The reader reports newer load configurations such as Control Flow Guard as unsupported.

For a MOD folder the diagnostic scans the selected directory and its `SKSE/Plugins` and `Data/SKSE/Plugins` directories. It resolves up to three supporting DLLs for each plugin using their file and exported function names. Shared dependencies are initialized once. The loader chooses disjoint virtual addresses when the preferred addresses overlap. Selection is limited to 16 files and 64 MiB. The diagnostic reports missing, ambiguous and cyclic dependencies before initialization.

The emulated Windows calls include private memory allocation, thread-local values, last-error state, recursive critical sections and 32-bit Interlocked operations. Each DLL with static TLS gets its own initialized block. Its process attach and detach callbacks run in Windows order inside the same bounded diagnostic. A read-only scan of Classic JContainers 3.3.0 found 181 imports and static TLS. A gameplay trial still needs broader Windows services and live SKSE interfaces. For an unbound import or refused Windows operation, the screen can name the responsible function or helper.

`HeapCreate` supports growable private heaps with zero flags or `HEAP_NO_SERIALIZE`. The interpreter serializes guest heap calls. Handles are distinct within a diagnostic process and are retired on `HeapDestroy`, which removes only the private heap's own allocations. Private and process heaps share one lazy 1 MiB arena and a 1,024-allocation limit, with up to 16 live private handles. Fixed-size, executable and exception-generating heap requests stop with an unsupported API result. The CRT, process heap and protected environment storage retain their existing ownership rules.

Plugins can also resolve approved names from the virtual `kernel32` and `msvcrt` libraries. Both named and static lookups use the same service table. Module handles and function addresses are diagnostic values. `GetModuleFileNameA/W` returns virtual Windows paths for the game executable, the built-in modules and named mapped DLLs. The session has a virtual process ID. Clock services provide UTC in `FILETIME` units and a monotonic counter with its frequency.

`GetCommandLineA` returns the virtual game path stored in guest memory. `EncodePointer` and `DecodePointer` use one randomly initialized key per guest process. The encoding applies to guest values for that process's lifetime.

`GetStartupInfoA/W` use the same verified PE32 layout for the isolated GUI guest. The guest has no shell startup strings or inherited console handles, so these flags and pointers are not copied from the host. `SetHandleCount` returns the requested count and preserves last error, matching the Windows PE32 reference.

The virtual PE32 CPU supports `PUSHFD` and `POPFD` for arithmetic and direction flags. The reserved bit and the user-mode interrupt-enable bit read as set. Other unsupported flags read as clear and ignore writes. This includes the ID flag, so a guest can detect that `CPUID` is unavailable. `IsProcessorFeaturePresent` reports only the interpreter's enforced non-executable data permission.

The text services convert UTF-16 to and from UTF-8 and Windows-1252. The guest's ANSI code page is 1252. Conversion uses bounded guest buffers and reports unsupported encodings and flag combinations explicitly. UTF-8 can represent Japanese text. Windows code page 932 is outside the current diagnostic support.

`VirtualProtect` changes read-only, read/write and inaccessible states on 4 KiB pages within one mapped DLL data section. It reports the first page's previous protection. The page state follows the mapping between calls and is freed with it. Executable sections, headers, sub-page images and external addresses are outside this service's supported range. All mapped pages remain ordinary host data.

The folder diagnostic can supply read-only file snapshots to these calls from the selected MOD. The VM understands relative paths, including UTF-16 names, and reads each file into an immutable payload before exposing a virtual handle. A diagnostic can hold four files open, read up to 1 MiB per file and open 4 MiB in total. Synchronous reads, file sizes, 32-bit and 64-bit seeks, end-of-file and handle closure use the Windows ABI. A successful `SetFilePointer` whose low word matches the failure sentinel clears the last error. Attribute lookups report regular files and directories with no content reads. Exact path components use one metadata lookup. A missing component can be resolved by an unambiguous ASCII case match inside the selected directory, with up to 4,096 entries examined per operation. A file chooser that grants a single DLL does not grant its folder.

`CreateFileA/W`, `WriteFile` and `SetEndOfFile` support temporary outputs in guest memory. `C:\Skyrim\` and relative paths use the same guest directory. Up to four outputs of 1 MiB each survive handle closure and can be reopened until the diagnostic session ends. The handles track access, sharing and current position independently.

Dot components are resolved inside the virtual game root before looking up files. This covers a configuration path such as `StorageUtilData/../WearableLanternsData` under the shared Plugins directory. An upward escape fails. The resulting path still uses the read-only source and session-local writes.

The experimental synchronization services track unnamed manual-reset and auto-reset events and counting semaphores in the same virtual process. A wait can mix events and semaphores. Waiting for all of them consumes their signals or counts only if every object is ready.

A single-module diagnostic can run one logical Windows worker at a time. It has its own stack, static and dynamic TLS values and last-error state. The worker runs when the caller joins it with an infinite single-object wait or when the last startup callback has returned. The trial keeps its execution budget, and closing the handle leaves the worker eligible to run. Worker startup and termination notify the DLL. Finite waits on active workers, nested workers, mixed worker waits and alertable waits are reported as unsupported.

The Classic Task interface accepts up to 16 pending delegates in each of its game and UI queues. The diagnostic drains each queue in submission order after initialization. It calls the delegate's current `Run` and then `Dispose` as i386 virtual methods. Tasks added during a callback stay behind already-queued entries of that type. All callbacks run in the isolated diagnostic and share its work budget.

The resident session test opens the same validated image and completes `Query` and `Load` before returning ownership to the host. `PostLoad`, `PostPostLoad`, the two task queues and worker execution are explicit host steps. The registry, TLS, mapped images, queues and records belong to the session until close. The host supplies an uptime sample and a bounded work allowance per step. Separate synthetic sessions retain independent state, and a failing callback stops only its own session. Game and UI threads still need verified call sites before using this API during play.

The Classic v4 serialization trial can run one DLL's registered save, revert and load callbacks against authored records. It checks stream writes, partial reads, skipped record tails and end-of-stream. A verified generation can supply the mod-index map to an isolated load callback. The supported methods preserve unresolved output and use the Classic index byte for forms and 64-bit handles. Live form deletion still needs a verified game event. [Generation scope](../skse-cosave/README.md)

`bench_x86.c` measures process CPU time for authored arithmetic, PE data access and calls through a full service table. For 250,000 short invocations, indexing the 64 validated service addresses reduced the median CPU time from 0.359 to 0.109 seconds on the Windows host over nine paired samples. This benchmark measures diagnostic startup and dispatch on the host.

Local file and folder diagnostics first try all named imports with their normal implementations. If linking stops at a recognized Windows CRT import, they can retry with stop-only bindings for the recognized set. Calling one of these functions ends the trial and reports its name. An initialization that returns with these bindings is reported as partial. An unknown import remains an image error, and a resident session still requires implemented bindings.

Host tests can enable Classic Papyrus v1 registration and a shadow registry for an authored static integer function. The registration is linked to the DLL that supplied the executable callback. Its Run method receives an isolated frame, and results are accepted only as a typed VM integer and a successful i386 return. One integration test connects this to the separately staged AOT Classic publisher and checks that a refused return type leaves its engine VMValue unchanged.

The optional owned PapyrusUtil regression uses `SKYRIM_TEST_OWNED_PAPYRUS_ZIP` and `SKYRIM_TEST_OWNED_LE_EXE` with `python3 -B -m unittest -v test_probe_local_file` on POSIX. It checks the game's pinned PE hash, copies two file-backed 32-bit data words into a temporary read-only guest view, and runs `StorageUtil.dll` through the interpreter at the preferred and a relocated address. The report contains phase status and numeric guest addresses. The local files are opened read-only and are never needed for the ordinary authored test suite or Apple checks. The app's file picker supplies no game views.

The same test checks three numeric hook requests, the original integer leaf and a saved integer replay with an authored mod list. The opt-in companion test binds the records to an exact saved generation. A word-aligned scalar load may read the zero padding of its own general heap allocation, which covers the original word-at-a-time string scan. Bulk copies and stores still require the logical allocation range.

The owned test's shadow registry captures the DLL's actual native declarations. It stores each native descriptor and its typed argument table in one allocation and releases unused tail space after the constructor gives the arity. The PEX inventory compares scoped names, static status, parameter types and result types with the registration. It identifies encoded static call sites without inferring reachability or instance dispatch. Of 395 entries, 394 match. The shipped PEX names `MiscUtil.ScanCellNPCsByFaction`, while the captured registration names `MiscUtil.TESTScanCellNPCsByFaction`. The trial also resolves the original StorageUtil PEX's static `JsonUtil.IntListSet` call through the matching JsonUtil declaration and DLL registration, then executes that typed wrapper. [PEX reader](https://github.com/Orvid/Champollion/blob/main/Pex/FileReader.cpp)

The same opt-in suite runs the original `JsonUtil` integer, float and text getters and setters and verifies the results through the prepared Classic VM source with an authored VM registry. It matches each selected native against the selected `JsonUtil.pex` before preparing or publishing the methods. Supplying another valid script in its place leaves the stored profiles intact. Strings returned by the DLL are copied before its temporary JSON memory is freed. The VM receives its own fixed string reference. The host refuses stale result scopes and unterminated text before destroying the old result. An interpreted execution failure seals the registered trial and invalidates pending profile output.

The original DLL also stores separate integers and a Japanese string for projected forms. The save process writes its real records to a temporary Classic companion using the existing codec. A fresh process maps the DLL at a different address, changes the authored mod order and restores the values for the same form. A different form keeps its original default. A truncated companion and a valid companion with the wrong owner are refused without invoking the load callback. The test uses authored form projections and a temporary companion. The game-file and save-generation checks run separately. [Form lifetime experiment](../classic-form-projection/README.md) · [Verified save generation](../classic-save-roundtrip/README.md)

In a host trial with a 1,060-byte authored settings file, the first getter parsed the file once at about 1.20 million guest instructions. The original cold `JsonUtil.Load` parsed it twice, at about 2.15 million instructions. The Wearable Lanterns startup fixture checks the original `common.json` selection of profile 1, writes both files on first use and reads the common file in a later read-only preparation call. Disabling automatic load leaves the profile file unopened. With automatic load enabled, preparation warms the profile once. All 39 subsequent getters completed under 30,000 work units each without reopening either file. The measured maximum on the direct hosted path was 25,559. The 2 million ceiling and the separate aggregate allowance apply to the hosted fixture. The supported x87 subset carries a 64-bit significand under the default control word. It covers the transfer, arithmetic and compare operations needed by the tested CRT decimal path. Windows x87 comparisons cover 33,168 arithmetic cases. SSE2 widening and narrowing match all 132 native cases including ties, signed zeros, subnormals and NaN payloads. Unmodeled operations stop the call. A bounded UTF-16 scan combines one validated read-only loop while preserving exact instruction counts, register results and flags. [Intel instruction reference](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)

The app option `SKYRIM_IOS_SKSE_DLL_PROBE` defaults to OFF. In an experimental build, open Settings → MOD → Details → DLL Compatibility. Remaining work includes plugin gameplay, broader Windows support, engine interfaces and ENB rendering. The diagnostic runs only when opened, outside the ordinary rendering path.

The separate `SKYRIM_IOS_CLASSIC_SETTINGS_PROBE` option exercises known
PapyrusUtil 3.3 settings in the app's launch sequence. Set it to `1` alongside
`SKYRIM_IOS_CLASSIC_SKSE=1` and `SKYRIM_IOS_SKSE_DLL_PROBE=1` for
`scripts/build-title-host.sh`. It requires the opted-in named profile's paired
DLL and PEX from its finalized game view. An accepted launch reports
`IOS_CLASSIC_SETTINGS_PROBE open_status=0` and checks a read of the common
Wearable Lanterns settings. Gameplay publication is pending verification of
the real VM frame lifetime. The host fixture exercises the exact owned DLL
and demonstrates that a rejected save acknowledgement preserves the last
published settings.

The tests generate their own DLLs. On Windows, `python -B -m unittest -v test_pe_image test_skse_plugin_vm test_dependency_plan test_classic_pex test_x86_sse_conversion` compares interpreted initialization to authored DLLs run by Windows, including relocations, allocated memory, thread-local values, callbacks and the attach and detach order of a four-DLL package. On Mac, `bash test-apple-sdk.sh` also checks the iPhoneOS sources and runs the same UI controller in an iOS simulator. It supplies selected URLs to the document picker's delegate and verifies the isolated diagnostic results in English and Japanese. Physical Files providers and gameplay need separate tests.
